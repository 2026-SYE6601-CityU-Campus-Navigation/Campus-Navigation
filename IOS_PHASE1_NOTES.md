# RoomMarker iOS Phase 1 Notes

## Scope delivered

Phase 1 establishes the native iOS foundation only:

- iOS 17 SwiftUI application and unit-test targets;
- minimal “RoomMarker / iOS Foundation Ready” launch screen;
- seven SwiftData models and their relationships;
- persistence container, first versioned schema, and destructive-operation repository boundary;
- HarmonyOS v1 / iOS v2 Codable DTO foundation;
- synthetic compatibility fixtures and automated tests;
- root repository hygiene rules.

No Phase 2+ feature was added. There is no CRUD UI, sensor manager, recording service, camera, map, navigation/routing, final exporter, ZIP writer, background capability, or share UI.

## SwiftData identity strategy

Every persisted model owns an application-generated, unique `UUID`. SwiftData still manages its internal persistent identifiers; the UUID is a stable application identity for relationships, testing, and future filesystem references.

HarmonyOS integer database primary keys are not reproduced. Those IDs are local storage implementation details and are not present in HarmonyOS track JSON objects. Future export filenames may use a safe UUID-derived token, while the manifest remains the authoritative reference. Persistence objects will be mapped into DTOs; they will never be encoded directly.

All Harmony-compatible timestamps are stored as `Int64` Unix epoch milliseconds. Optional sensor/location readings use optional `Double` values, preserving “unavailable” rather than substituting zero.

## Relationships and delete rules

| Parent | Child | SwiftData rule | Intended result |
|---|---|---|---|
| Area | Room | Nullify | Deleting an Area preserves the Room and sets `room.area` to nil. |
| Area | Track | Nullify | Deleting an Area preserves the Track and sets `track.area` to nil. |
| Room | Marker | Cascade | Deleting a Room deletes its Marker children. |
| Track | TrackPoint | Cascade | Deleting a Track deletes its sampled points. |
| Track | TrackTag | Cascade | Deleting a Track deletes its tag metadata. |
| Track | TrackPhoto | Cascade | Deleting a Track deletes photo metadata; future photo-byte cleanup remains a separate filesystem responsibility. |

`SwiftDataRepository.deleteAreaPreservingContents` explicitly clears child area relationships before deleting the area, in addition to the `.nullify` model rule. This makes the product operation intentional and testable instead of relying on a direct context deletion from feature code.

## Unassigned-area semantics

There is no persisted “未分区” Area and no magic identifier such as HarmonyOS UI ID `0`. A Room or Track with `area == nil` is unassigned. A future UI query will group nil-area objects under the display label “未分区”.

The synthetic `unassigned_room.json` fixture and SwiftData deletion test cover this state.

## Domain enum compatibility

`MarkerType` and `TrackTagType` are typed, Codable Swift enums with the exact HarmonyOS Chinese raw values. SwiftData entities store the raw string and expose a typed optional computed property. Storing the string keeps the database forward-compatible with a future unknown value rather than forcing a destructive enum migration.

## HarmonyOS v1 JSON compatibility

Persistence and external JSON are deliberately separate:

- SwiftData models describe the local store and relationships.
- `ExportedTrackDTO`, `ExportedPointDTO`, `ExportedTagDTO`, `ExportedPhotoDTO`, and manifest DTOs describe the external contract.
- Optional DTO fields let the same decoder accept HarmonyOS v1 and the planned iOS v2 extension.

The synthetic HarmonyOS v1 track fixture contains a point with `wifiCount` and `wifiTop`, plus a tag and photo metadata. Tests confirm the DTO layer decodes these fields. The v1 manifest fixture also decodes without requiring iOS-only version/platform/capability fields.

This phase does not import DTOs into SwiftData and does not produce export files or ZIP archives.

## iOS DTO versioning direction

The planned iOS document uses:

- `version: 2`;
- `sourcePlatform: "ios"`;
- `capabilities.nearbyWifiFingerprint: "unsupported"`;
- no `wifiCount` or `wifiTop` key on iOS-created points.

All other shared fields retain HarmonyOS names, units, timestamp representation, and optionality. Final schema review and exporter implementation remain Phase 6 work.

## Wi-Fi capability decision

iOS-created `TrackPoint` models default to:

- `wifiAvailability == .unsupported`;
- `wifiCount == nil`;
- `wifiTop == nil`.

The optional Wi-Fi fields allow genuine legacy observations to be represented if a future approved import path needs them. They are not populated by iOS collection code. DTO encoding tests inspect the actual JSON object and prove the keys are absent rather than `0`, empty, current-network-only, or fabricated values.

This slightly refines the Phase 0 statement that Wi-Fi fields need not exist in iOS persistence: Phase 1 keeps them optional solely to preserve genuine external observations and makes unsupported state explicit. It does not create any Wi-Fi service or entitlement.

## Swift 6.4 considerations

- UI, SwiftData container setup, repositories, and tests that touch `ModelContext` run on `MainActor`, matching SwiftData context isolation.
- Complete strict-concurrency checking is enabled; no `@unchecked Sendable`, unsafe nonisolated annotation, or warning suppression was added.
- DTOs and enums are value types conforming to `Sendable` where they may later cross task boundaries.
- The repository has a single `ModelContext` owner. Later high-frequency recording work must introduce an appropriately isolated writer rather than passing contexts between tasks.
- Xcode's build setting names the stable Swift 6 language mode; the installed compiler reports Apple Swift 6.4.

## Automated validation

Validation was performed with temporary DerivedData outside the repository.

```sh
xcodebuild -list -project RoomMarker.xcodeproj

xcodebuild \
  -project RoomMarker.xcodeproj \
  -scheme RoomMarker \
  -sdk iphonesimulator \
  -configuration Debug \
  -derivedDataPath /private/tmp/RoomMarkerDerived \
  CODE_SIGNING_ALLOWED=NO \
  build

xcodebuild \
  -project RoomMarker.xcodeproj \
  -scheme RoomMarker \
  -destination 'platform=iOS Simulator,name=iPhone 18 Pro,OS=27.0' \
  -configuration Debug \
  -derivedDataPath /private/tmp/RoomMarkerDerived \
  CODE_SIGNING_ALLOWED=NO \
  test
```

At Phase 1 completion, the app compilation succeeded, the test bundle built, and 13 Swift Testing tests across two suites executed successfully on the iPhone 18 Pro iOS 27 simulator. These tests cover all seven persisted model concepts, all required relationships/delete semantics, an interrupted track, enum raw values, v1 track/manifest decoding, synthetic unassigned data, and non-fabricated iOS Wi-Fi JSON.
